# 自动记账三大通道 Spec：无障碍捕获 / 通知监听 / 分享OCR

## Why

当前应用已有「AI 截图提示词 → JSON 导入」流程，但仍有三个缺口：
1. 用户付完账后需要手动去截图、发给 AI、等 JSON 再回来导入——步骤太多；
2. 支付宝 / 微信 / 京东等 APP 内部账单列表页面信息丰富但无导出入口——需要能「看一眼就记录」；
3. 支付通知栏消息包含了关键金额和商户信息——白白浪费。

本 Spec 定义三个互补的自动记账数据通道，全部汇聚到统一的「待确认账单」入口，保持「人机交互」原则：系统识别 → 弹窗确认 → 用户点头入账。

## What Changes

- **新增 Android 无障碍服务 AccessibilityService**：监听白名单 APP（微信、支付宝、京东、美团、抖音）的窗口变化，识别支付成功页和账单列表页面的文本内容，提取金额/商户/时间/账户等字段。
- **新增 Android 通知监听服务 NotificationListenerService**：接收支付 APP 的支付结果通知，作为无障碍服务的兜底。
- **新增分享接收 + 本地 OCR**：接收用户通过系统分享菜单发来的支付截图/账单截图，使用 ML Kit 进行文字识别。
- **新增「待确认账单」页面**：三个通道的识别结果统一汇聚到此页面，用户确认后入账。
- **新增 Android Room 捕获队列数据库**：原生层暂存捕获事件（解决 APP 不在前台时无法推送 WebView 的问题）。
- **新增统一支付解析器 Registry**：按来源 APP 包名 + 解析器版本路由到对应适配器。
- **新增权限引导与状态诊断页**：引导用户开启无障碍/通知权限，并显示服务健康状态。

无 BREAKING 变更。所有通道均为用户主动开启的增强能力，关闭后不影响已有功能。

## Impact

- 新增 Android 原生代码（Kotlin）：AccessibilityService、NotificationListenerService、ShareActivity、Room Database、Capacitor 本地插件。
- 新增 AndroidManifest.xml 声明（服务、权限、intent-filter）。
- 新增前端页面：`CaptureInboxView.vue`（待确认账单）。
- 新增前端功能模块：`features/capture-inbox/`（解析、去重、确认逻辑）。
- 新增 SQLite 表：`capture_queue`（捕获队列）。
- 依赖新增：`com.google.mlkit:text-recognition`（OCR）。
- 技术选型文档中阶段 C 的实现。

## ADDED Requirements

### Requirement 1: 无障碍服务 — 支付页面自动识别

系统 SHALL 在用户主动开启无障碍服务后，实现以下能力：

1. **白名单监听**：无障碍服务仅监听配置的白名单包名列表（初始：`com.eg.android.AlipayGphone` 支付宝、`com.tencent.mm` 微信、`com.jingdong.app.mall` 京东、`com.sankuai.meituan` 美团、`com.ss.android.ugc.aweme` 抖音）。
2. **窗口变化监听**：注册 `TYPE_WINDOW_STATE_CHANGED` 和 `TYPE_WINDOW_CONTENT_CHANGED` 事件。当白名单 APP 的前台 Activity 切换到支付成功页、转账结果页或账单详情页时，触发识别。
3. **页面文本提取**：通过 `AccessibilityNodeInfo` 遍历当前窗口可视节点的文本内容，提取关键字段（金额、商户名、时间、付款账户、订单号等）。
4. **只读约束**：无障碍服务**不点击、不输入、不执行手势**，仅读取屏幕内容。
5. **支付成功页适配**：至少覆盖支付宝扫码支付成功页、微信付款成功页的文本解析。
6. **账单页面适配**：当用户在支付宝/京东的「账单」列表页时，无障碍服务识别当前可见的账单条目，每条账单弹出一个「识别到账单，是否记入？」的确认卡片。
7. **隐私保护**：不读取密码输入框、短信验证码、聊天内容、联系人列表。识别过程中不保留原始节点树。
8. **去重**：相同来源 APP + 相同金额 + 1 分钟内的事件合并为一条，避免重复弹窗。

#### Scenario 1.1: 用户支付宝扫码付款成功
- **WHEN** 用户在支付宝完成扫码支付，支付成功页显示「支付成功 ¥48.50 商家：海底捞 支付账户：支付宝余额」
- **THEN** 无障碍服务检测到窗口变化，解析出金额 ¥48.50、商户「海底捞」、付款账户「支付宝余额」
- **AND** 原始数据写入 Room 捕获队列
- **AND** 当用户切回财务经理 APP 时，弹出一个确认卡片显示识别结果
- **AND** 用户点确认后入账为一条支出记录

#### Scenario 1.2: 用户查看支付宝账单列表
- **WHEN** 用户打开支付宝「账单」列表页，列表展示了最近 10 条交易
- **AND** 无障碍服务识别出当前可见的账单条目
- **THEN** 财务经理 APP 弹出一个「识别到 X 条账单」的汇总卡片
- **AND** 用户可选择「全部确认」「逐条确认」「忽略」

#### Scenario 1.3: 无障碍服务被系统关闭
- **WHEN** 系统在休眠后被 Android 关闭了无障碍服务
- **THEN** 下次用户打开财务经理时显示一条提示「无障碍服务已停止，如需自动捕获请重新开启」
- **AND** 提示中提供「前往设置」按钮，跳转到系统无障碍设置页

### Requirement 2: 通知监听服务 — 支付通知自动捕获

系统 SHALL 在用户主动开启通知监听权限后，实现以下能力：

1. **白名单通知过滤**：仅处理白名单 APP 的通知，其他 APP 的通知完全忽略。
2. **通知内容解析**：从通知文本中提取金额、商户名、交易类型。
3. **通知事件暂存**：将解析结果写入捕获队列，等待用户打开 APP 时展示。
4. **服务状态检查**：每次 APP 启动时检查通知监听权限是否仍有效。

#### Scenario 2.1: 微信支付通知
- **WHEN** 用户用微信支付了一笔消费，微信发出通知「微信支付 商户：星巴克 ¥18.00」
- **THEN** 通知监听服务捕获该通知并解析出金额 ¥18.00、商户「星巴克」、来源「微信支付」
- **AND** 当用户打开财务经理 APP 时，捕获结果进入「待确认账单」

### Requirement 3: 分享接收 + 本地 OCR

系统 SHALL 实现以下能力：

1. **注册分享接收入口**：在 AndroidManifest.xml 注册 `ACTION_SEND` intent-filter（text/plain 和 image/*），支持系统分享菜单。
2. **文本分享处理**：用户分享支付结果文本时直接提取关键字段。
3. **图片分享处理**：用户分享支付截图时，使用 ML Kit Text Recognition v2 在本地进行 OCR，提取金额/商户/时间等文本。
4. **OCR 结果去重**：OCR 识别结果与捕获队列中的已有记录进行指纹比对，避免同一截图被重复记录。
5. **OCR 隐私**：识别后的截图图片立即释放，不持久化到相册。

#### Scenario 3.1: 用户分享截图给财务经理
- **WHEN** 用户在相册或支付 APP 中选中一张支付成功截图，点击「分享」→「财务经理」
- **THEN** 财务经理接收图片并启动 ML Kit OCR
- **AND** OCR 识别出金额 ¥128.00、商户「京东商城」、时间「2026-08-10 14:30」
- **AND** 结果进入「待确认账单」，用户确认后入账

### Requirement 4: 待确认账单页面

系统 SHALL 提供一个「待确认账单」页面，作为三个通道的统一出口：

1. **列表展示**：以时间倒序展示所有未确认的捕获记录，每条显示：金额、商户、来源 APP 图标、捕获方式（无障碍/通知/OCR）、捕获时间。
2. **确认操作**：用户点「确认」后入账为支出/收入记录，需选择（或系统推荐）分类和账户。
3. **忽略操作**：用户可删除单条或全部忽略。
4. **编辑操作**：用户可修改识别出的金额、商户、账户、分类。
5. **去重提示**：如果同一条已存在（基于金额+时间+商户指纹），自动标记为「疑似重复」并阻止确认。
6. **解析信息可追溯**：每条记录显示来源 APP、捕获方式、解析器版本号，方便排查误识别。

#### Scenario 4.1: 一条记录从捕获到入账
- **WHEN** 无障碍服务识别到一笔支付宝消费
- **AND** 用户打开「待确认账单」页面
- **THEN** 页面显示该条记录，推荐账户「支付宝余额」、分类「餐饮」
- **AND** 用户点确认后入账
- **AND** 记录从待确认列表消失

### Requirement 5: 统一捕获队列（Room）

系统 SHALL 在原生层维护一个独立于正式账本的捕获队列数据库：

1. **表结构**：`capture_queue` 包含字段 `id, source_package, capture_method, occurred_at, amount_minor, merchant, account_hint, source_order_id, raw_fingerprint, confidence, parser_version, status, created_at`。
2. **存储策略**：原始识别文本（notification title/text、accessibility 节点树）仅在解析时短暂保留，**不持久化**到队列，只保存结构化字段和指纹。
3. **生命周期**：记录在用户确认后从队列中删除。超过 30 天未确认的记录自动标记为过期并提示用户清理。
4. **并发安全**：队列写入使用 Room 的 suspend 函数，由协程管理。

### Requirement 6: 权限引导与状态诊断

系统 SHALL 提供一个「自动记账设置」页面：

1. **无障碍服务开关**：显示当前状态（已开启 / 未开启 / 被系统关闭），提供跳转设置按钮。
2. **通知监听开关**：同上。
3. **服务健康状态**：显示「最近一次捕获时间、来源 APP、解析器版本、服务是否在运行」。
4. **自检功能**：提供「运行自检」按钮，检查各服务是否可正常接收测试事件。
5. **白名单管理**：用户可启停各个 APP 的自动捕获。

## 技术可行性结论

### 无障碍服务能做到的程度

| 能力 | 是否可行 | 说明 |
|---|---|---|
| 监听支付 APP 窗口变化 | ✅ 可行 | `TYPE_WINDOW_STATE_CHANGED` + 包名过滤 |
| 读取支付成功页文本 | ✅ 可行 | `AccessibilityNodeInfo` 遍历节点文本 |
| 截图支付页面 | ⚠️ 有限可行 | API 26+ `takeScreenshot()`，但有延迟，仅静态页面可用 |
| 点击/操作页面 | ❌ 不做 | 明确禁止自动操作，仅限只读 |
| APP 不在前台时监控 | ✅ 可行 | AccessibilityService 是系统级服务，不依赖 WebView |
| 数据传递到前端 | ✅ 可行 | 原生层写 Room → 用户切回 APP → 插件推事件 |

### 三个通道的互补关系

```
支付场景
  ├── 支付成功页弹起 → 无障碍服务（最快、最准）
  ├── 通知栏弹出     → 通知监听（兜底，APP 不发通知页时覆盖）
  └── 用户手动分享截图 → 分享+OCR（终极兜底）
       ↓
   Room 捕获队列
       ↓
  用户打开 APP → 待确认账单 → 确认后入账
```

### 为什么必须用 Android 原生

- AccessibilityService 是 Android 系统 API，只能在原生层实现，无法通过 Capacitor 纯 JS 调用。
- 但架构复用现有模式：原生插件（Java/Kotlin）→ Capacitor 桥接 → Vue 前端，与现有 `ClipboardReaderPlugin` 完全一致。
- 捕获队列用 Room 独立存储，不依赖 WebView 存活，解决 APP 不在前台时的数据传输问题。
