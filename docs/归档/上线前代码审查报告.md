## 一、总体结论

**当前状态：不建议直接发布。** 存在 6 个功能性阻塞缺陷（其中"确认入账"主链路必然失败属于链路级断裂）、1 个合规决策项、以及版本管理层面的发布流程缺口（v1.1.0 全部功能代码尚未提交，历史上从未产出过签名 release 包）。

架构底座是健康的：金额全程分为整数（`amount_minor` + CHECK 约束）、核心记账在单事务内原子提交、余额走视图读时聚合（天然规避余额列并发问题）、迁移 runner 有前缀校验/回滚/未知版本拒绝、仓库层 90% 参数绑定、255 个前端测试全部通过、release 构建可编译通过。**问题集中在自动捕获链路的"最后一公里"和三个新迁移（011/013/014）带来的 schema 双头维护漂移。**

## 二、存在问题（按严重程度排序）

### P0 —— 功能阻塞，发布前必须修复

**P0-1 「确认入账」主链路必然失败：异步上下文调用 `inject()` 恒返回 undefined** ⚠️已复核
- 位置：`app/src/features/capture-inbox/capture-inbox-service.ts:40`
- `useFinanceService()` 是 `inject(financeServiceKey, undefined)` 的包装（`finance-service.ts:1642-1645`）。Vue 规定 `inject()` 只能在 setup 同步栈中调用；而 `confirmEvent` 的三个调用点全部在异步上下文：`App.vue:448`（悬浮窗提交回调）、`stores/capture-entry.ts:231`（当场弹窗确认）、`CaptureInboxView.vue:130`（待确认列表确认）。
- 后果：无障碍/通知捕获 → 待确认列表 → 点"确认入账"→ 必然抛"账务服务不可用"。**自动记账的三条确认路径全部断裂。**
- 讽刺点：`main.ts:77-78` 已建好全局兜底（`window.__financeService` 与 `appStore.financeService`），`confirmEvent` 漏用了。
- 修法：`const finance = (window as any).__financeService ?? useAppStore().financeService`，或作为参数传入 `ConfirmInput`。

**P0-2 收入/转账方向的捕获确认后被记成"支出"** ⚠️已复核
- 位置：`capture-inbox-service.ts:45`（硬编码 `finance.createExpense`）
- 捕获事件携带 `direction` 字段（`payment-capture-reader.ts:39`），默认规则中 `wechat-redpacket`（收红包，income）、`lingqiantong-out/withdraw`（transfer）都会进队列，确认后一律落库为支出——方向反转、余额算错。确认弹窗 UI（`CaptureInboxView.vue:303-383`）也只有支出分类/付款账户两组字段。
- 修法：按 `event.direction` 分派 `createIncome`/`createTransfer`；至少 income/transfer 方向时强制跳转完整记账页。

**P0-3 入账成功后清理队列失败 → 误报"入账失败" → 诱导重复入账** ⚠️已复核
- 位置：`capture-inbox-service.ts:62`
- `createExpense` 成功后，`acknowledgeEvents` 无 try-catch；抛错则 UI 显示失败，用户再点 → 同一笔账入两条（指纹标记在 L64-66，位于 L62 之后执行不到）。
- 修法：L62 包 try-catch（账已入，队列清理失败只影响去重不应回报失败）；或入账前先 acknowledge。

**P0-4 文字分享记账整条链路必然失败（主线程 Room 写入被吞异常）** ⚠️已复核
- 位置：`PaymentShareActivity.java:57-75 / 222-224 / 245-247`
- `handleTextShare()` 在 onCreate（主线程）同步调 `dao.insert()`，而 `CaptureQueueDatabase`（`CaptureQueueDatabase.java:79-83`）未开 `allowMainThreadQueries()` → Room 抛 `IllegalStateException` 被 `catch (Exception e)` 吞掉，但用户已看到"已识别到支付信息"Toast。且 `CaptureDedup.isDuplicate()` 在插入前已标记 key，2 分钟内重试也被内存去重拦掉。
- 修法：`writeCaptured` 全部移入后台 executor，成功后再 Toast/finish。

**P0-5 minSdk=24 却使用 `java.time.Instant`，Android 7.x 设备必崩** ⚠️已复核
- 位置：`PaymentShareActivity.java:230`；`variables.gradle:3` minSdkVersion=24；未启用 coreLibraryDesugaring
- `java.time` 需 API 26+，未脱糖时 API 24/25 设备分享文本直接 `NoSuchMethodError` 崩溃。
- 修法：改 `System.currentTimeMillis()`（与通知/无障碍链路一致）。

**P0-6 通知/分享通道的持久指纹掺入随机数，DB 去重层对这两条通道完全失效** ⚠️已复核
- 位置：`PaymentNotificationListenerService.java:163-169`（`UUID.randomUUID().substring(0,8)`）、`PaymentShareActivity.java:254-267`（`randomToken()`）
- 同一笔支付每次生成的 `rawFingerprint` 都不同 → `capture_fingerprint` 表对这两条通道形同虚设，去重只剩 2 分钟内存桶（`CaptureDedup`），进程重启后同笔重复可穿透。
- 修法：指纹改为 `pkg:method:amount:merchant:分钟桶` 或与无障碍一致的 `tx:hash(金额|时间|商户)`。

**P0-7 备份/恢复丢列：011/013/014 三次迁移新增的列不在备份 schema 里** ⚠️已复核
- 位置：`features/backup/backup-repository.ts:26-37`（accounts 缺 `sort_order`）、`:87-104`（import_batches 缺 `execution_errors_json`）、`:107-125`（transactions 缺 `fingerprint`）
- v14 备份→恢复后：所有 `transactions.fingerprint` 变 NULL（014 的防重能力整体丢失）、账户拖拽排序归 0、导入错误详情丢失。恢复不报错，纯静默丢失。
- 修法：TABLE_SCHEMAS 补 3 列；并加 `PRAGMA table_info` 与 TABLE_SCHEMAS 的自动一致性校验测试，杜绝双头维护漂移。

**P0-8 恢复旧版本备份会把应用"变砖"** ⚠️已复核
- 位置：`features/backup/restore-service.ts:29-49` + `backup-repository.ts:13`（`schema_migrations` 本身也在备份表清单中，replaceAll 全表覆盖）
- 恢复 ≤v14 的旧备份会把当前库的迁移记录打回旧版本，下次启动重复执行非幂等迁移（`ALTER TABLE ADD COLUMN` 报 duplicate column）→ `main.ts:56-59` 进入数据库错误态，应用不可用。
- 修法：replaceAll 不还原 `schema_migrations`（保留当前库记录），或恢复走"空库重建→全量迁移→仅还原数据"流程。

**P0-9 迁移前自动备份把旧数据标成最新 schema 版本** ⚠️已复核
- 位置：`db/bootstrap.ts:125`（`schemaVersion: LATEST_SCHEMA_VERSION`，此时数据实际还是旧版本）
- 迁移 013 成功、014 失败的场景下，用该备份恢复正好触发 P0-8。
- 修法：从 `schema_migrations` 取 dump 时刻的真实 max 版本号。

### P1 —— 高优先级（功能性/安全/合规）

**P1-1【合规·决策项】无障碍服务伪装成系统 "Select to Speak"** ⚠️已复核
- 位置：`com/google/android/accessibility/selecttospeak/SelectToSpeakService.java`（注释自述："伪装成系统'选择朗读'无障碍服务，绕过微信 8.0.52+ 的节点混淆白名单"）；`AndroidManifest.xml:68`
- 类名冒充 Google 系统应用包名空间，直接命中 Google Play"冒充/欺骗"政策，也违反微信用户协议；同时它是 `minifyEnabled=false` 的根因（R8 重命名会破坏伪装）。上架 Play 即高危下架风险；仅侧载分发则需接受微信对抗升级。
- 需要产品层决策：改名+接受可能失效、或放弃 Play 渠道仅侧载。

**P1-2 Shizuku 守护线程每 30 秒无视用户开关强制重新启用无障碍**
- 位置：`capture/shizuku/user/UserService.java:45-101`（无任何开关判断，直接 `settings put secure enabled_accessibility_services` 写回）
- 应用侧 `AccessibilityAutoRecover.setEnabled(false)` 管不到 daemon 进程。用户主动关闭服务后 30 秒内被强行写回——行为与合规双重风险（应用绕过用户意志自我提权）。
- 修法：恢复动作必须由应用侧带开关的调用触发；daemon 只做"检测+通知"。

**P1-3 Shizuku 失败返回 `""` 被当成功——冷启动"恢复成功"是假象**
- 位置：`ShizukuShell.java:189-212`（失败返回 ""）+ `:157-175`（异步绑定，连接建立前 exec 必返回 ""）+ `AccessibilityEnabler.java:79-86`（`result != null` 恒 true）
- `AccessibilityAutoRecover.checkAndRestore()` 与 `ShizukuBootReceiver.onReceive` 冷启动首次调用全部误报成功，实际一条命令未执行。
- 修法：exec 失败返回 null，调用方校验真实回执，绑定完成后重试一次。

**P1-4 无障碍节点树被三个解析器重复遍历，且 `extractVisibleText` 会 recycle 全部节点（含 root）——API ≤32 设备捕获链路损坏**
- 位置：`PaymentParserAdapter.java:36-55`（finally 里对每个节点含 root recycle）；`PaymentAccessibilityService.java:370-405`（同一 root 依次跑 3 个解析器）；`:283-288`（对已回收 root 再 recycle）
- 在启用节点对象池的系统（约 API ≤ 32）上，第一个解析器回收后，后续解析器读到已回收节点返回空文本 → 详情规则未命中时兜底解析全部失效。
- 修法：去掉手动 recycle（API 33+ 已废弃为 no-op），或每轮只提取一次文本传给所有解析器复用。

**P1-5 支付敏感信息明文进 logcat，Release 包未剥离**
- 位置（部分）：`WechatAdapter.java:44-45`（页面前 300 字符全文）、`PaymentNotificationListenerService.java:79`（通知全文）、`ClipboardReaderPlugin.java:58/76-78`（剪贴板内容前 60-80 字符，可能是密码/验证码）、`PaymentShareActivity.java:63/116/150`、`AccessibilityDiagnostics.java:119-136`（商户+金额+页面片段进环形缓冲，`exportDiagnosticLog` 可一键分享给任意应用）
- `minifyEnabled=false` 且 `proguard-rules.pro` 为空模板，Release 包所有 `Log.d` 保留。
- 修法：统一日志门面（BuildConfig.DEBUG 门控或 R8 `assumenosideeffects` 剥离 `Log.d/v`）；诊断导出前对金额/商户/文本片段脱敏。

**P1-6 PIN 码弱哈希 + 备份含 PIN 哈希落公共目录**
- 位置：`features/app-lock/app-lock-service.ts:108-112`（单轮 `SHA-256(salt:pin)`，无迭代）、`:58-66`（验证无错误次数限制）；`utils/file-io.ts:48-54` 与 `db/bootstrap.ts:134-140`（备份 JSON 写 `Directory.Documents`，且包含 `app_settings` 即 PIN hash/salt，未加密）
- 4-8 位纯数字 PIN + 备份外泄 = 离线秒破。
- 修法：PBKDF2（≥10 万轮）+ 尝试次数节流；备份默认写应用私有目录，导出由用户显式分享；或至少把 app_settings 排除出备份。

**P1-7 编辑交易丢失 fingerprint 与 import_batch_id，破坏 014 防重和导入批次撤销**
- 位置：`transaction-repository.ts:149-261`（replace 只 void 旧交易插新交易，不回填两字段）；`finance-service.ts:288-303`（`EditTransactionFullInput` 无 fingerprint/captureSource）
- 编辑过的导入交易脱离批次（撤销批次后编辑版仍生效）；被编辑的自动记账交易 fingerprint 变 NULL，可被再次捕获成重复账单。
- 修法：replace 时从旧交易复制 `import_batch_id/fingerprint/capture_source/parser_version/confidence`。

**P1-8 importBatch.voidBatch 逐条 UPDATE、每条独立事务，非原子**
- 位置：`import-batch-repository.ts:248-271`
- 中途崩溃 → "半撤销批次"（部分交易已 void 且余额已回退、部分仍 posted、批次还是 active）。注释称是绕 executeSet 绑定 bug，但完全可用单条 `UPDATE ... WHERE id IN (...)` 参数绑定完成。
- 修法：合并为一条 IN 更新 + 批次标记同一事务。

**P1-9 迁移失败后连接残留 `PRAGMA foreign_keys = OFF`**
- 位置：`migration-runner.ts:48-56`（data 段抛错直接冒泡，无 try/finally 恢复）
- executor 是全局复用单连接，之后所有写入失去外键保护。
- 修法：runMigrations 用 try/finally 保证任何失败路径补 `PRAGMA foreign_keys = ON`。

**P1-10 多实体写操作无事务包裹**
- 位置：`finance-service.ts:830-884`（createReceivable = 账户+交易+台账三段独立提交）、`:939-992`（createPayable 同构）、`:627-687`（createAccount 四段）
- 中途失败留下无台账的借出账户、或无期初交易的空账户。
- 修法：给 SqliteExecutor 增加 `withTransaction(cb)`，把这些多步写包进同一事务。

**P1-11 "X 元"格式的金额永远解析不出** ⚠️已复核
- 位置：`AlipayAdapter.java:35`（`[¥￥]\s*(\d+[.\d]*)|\d+[.\d]*\s*元`，第二分支无捕获组）+ `extractFirst(...,1)` 只取 group(1)；同病：`GenericNotificationAdapter.java:14/45`、`GenericPaymentAdapter.java:13-14/51`、`WechatNotificationAdapter.java:22/44`
- 命中"48.50 元"分支时 group(1)==null → 整条支付信息被丢弃。
- 修法：拆成两个 Pattern，或对 null 分支回退取 group(0) 去掉"元"。

**P1-12 原生 → Web 的 `/capture-quick` 跳转链路与路由模式不匹配（已断链）** ⚠️已复核
- 位置：`router/index.ts:19`（`createWebHistory`，history 模式）vs `MainActivity.java:121/142`、`OverlayQuickEntryActivity.java:50`（注入 `location.hash='#/capture-quick?...'`）
- history 模式下改 hash 不触发 vue-router 导航（vue-router 监听 popstate 而非 hashchange）；全前端无任何 hashchange 监听（grep 0 命中）。悬浮窗入口（`OverlayEntryManager`）CHANGELOG 0.5.1 已称停用，原生侧也确认无调用方。
- 修法：确认不需要则整体删除（路由 + `CaptureQuickView.vue` + `OverlayQuickEntryActivity` 的 hash 注入）；要保留则改走 `checkPendingCaptureData()` 同一路径。

**P1-13 `@capacitor/filesystem` 与 Capacitor 8 跨大版本混用**
- 位置：`package.json:22`（`@capacitor/filesystem: ^7.1.8` vs `@capacitor/*: ^8.5.0`）
- 官方不支持的组合，7.x 原生代码编进 8.x 宿主。备份/导出功能全走它。
- 修法：升级到 8.x 并回归备份/导出。

**P1-14 v1.1.0 全部功能代码（39 个文件，+2754/-161 行）尚未提交** ⚠️已复核
- 35 个 M + 17 个新文件（含 013/014 两个迁移、`features/capture/`、keepalive 服务、DuplicateBlocker 等）全部只在工作区。HEAD（fea128e）只有 v1.0.0。误执行 `git checkout .` 即丢失 2700+ 行；产物无法从任何 commit/tag 复现。
