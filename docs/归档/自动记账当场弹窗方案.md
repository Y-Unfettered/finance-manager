# 自动记账「当场弹窗」改造方案

> 状态：待评审
> 更新日期：2026-10-19
> 目标：支付成功后，弹窗直接浮在微信/支付宝/淘宝等当前应用上层，用户当场完成分类与入账，不再切回本 APP。

| 入账逻辑 | `features/capture-inbox/capture-inbox-service.ts` | 已实现，调 `finance.createExpense` 写正式账本 + 标记队列已确认 |

### 1.2 为什么你现在体验是"只有金额、只能取消"

代码读下来，这个现象不是"没做"，而是两个具体断点叠加：

**断点 A：弹窗画在 WebView 里，必须切回本 APP 才看得见。**

- 无障碍服务识别成功后，`PaymentAccessibilityService.writeToQueue()` 调 `PaymentCapturePlugin.notifyCandidate(entity)`。
- 这个方法通过 Capacitor bridge 发 `paymentCaptureCandidate` 事件给 JS。
- `App.vue:298` 收到事件后调 `captureEntryStore.showEntry(data)`，把 `store.visible = true`。
- 但这个 `visible` 控制的是 Vue DOM 里的一个 `div`（`CaptureQuickEntrySheet.vue`），它画在记账 APP 自己的 WebView 里。**你人在微信前台时，这个 WebView 根本不在屏幕上。**
- 等你切回记账 APP，WebView 重新可见，弹窗才冒出来——这就是你说的"退回到记账软件时下面弹出一个弹窗"。

**断点 B：切回 APP 那一刻，账户/分类列表经常没加载出来。**

`capture-entry.ts:132 loadOptions()` 里：

```ts
if (!appStore.ledgerId || !finance) { this.loading = false; return }
```

切回 APP 时如果遇到冷启动 / 数据库还在打开 / 账本还没选中，`ledgerId` 是空的，这个方法直接 return，`accounts` 和 `categories` 就是空数组。

于是 `CaptureQuickEntrySheet.vue` 里：
- 分类区 `v-for="cat in store.categories.slice(0,10)"` → 空的，什么都不渲染
- 账户区同理 → 空的
- 确认按钮 `isConfirmDisabled = ... || !accountId || !categoryId` → 永远 disabled

你看到的就是：一个弹窗顶上有金额数字，下面一大片空白，右下角"确认入账"是灰的，只有右上角 X 和底部"忽略"能点。**这就是你说的"只能取消"。**

### 1.3 Manifest 里根本没有悬浮窗权限

读了 `app/src/main/AndroidManifest.xml`，权限只有：

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.READ_CLIPBOARD" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
```

**没有 `SYSTEM_ALERT_WINDOW`**。也就是说，当前架构在系统层面就不具备"在其他 APP 上层画东西"的能力。这是要补的硬前提。

## 2. 目标体验

```
微信支付成功页（¥12.50 给「瑞幸咖啡」）
        │
        │  无障碍服务识别到"支付成功" + 金额
        ▼
┌─────────────────────────────────┐
│  底部滑入一张紧凑卡片（原生View） │
│                                 │
│  ¥12.50        瑞幸咖啡  [微信] │
│  ─────────────────────────────  │
│  分类: ☕咖啡  🍜餐饮  🛒购物 ...│
│  账户: 招行卡  支付宝  微信 ... │
│                                 │
│  [忽略]              [✓ 记一笔] │
└─────────────────────────────────┘
        │
        │ 用户点「记一笔」（默认分类/账户已预选好）
        ▼
   卡片消失，屏幕中央一个 Toast：
   "已记账 ¥12.50 · 咖啡 · 招行卡"
        │
        ▼
   你还停在微信支付页，没切走任何 APP
```

关键体验点：
1. 不打断当前 APP（微信/淘宝保持前台，不清栈）
2. 默认值已经根据规则预选好（商户→分类、上次用的账户），熟练情况下点一下就完事
3. 全程不切回记账 APP
4. 出错（比如识别错金额）仍然可以在悬浮窗里改

## 3. 技术方案

### 3.1 路线对比

| 路线 | 原理 | 悬浮体验 | 工程量 | 权限要求 | 小米/HyperOS 风险 |
|---|---|---|---|---|---|
| **A. 原生悬浮窗（推荐）** | `SYSTEM_ALERT_WINDOW` + `WindowManager.addView` 直接在当前 APP 上层画 View | 真正浮在所有 APP 之上，微信不 onPause | 中（卡片 UI 原生重写，但很小） | 悬浮窗权限 | 中：需手动开"显示在其他应用上层"，Shizuku 可代开 |
| B. 透明 Activity | 无障碍 `startActivity` 拉起一个半透明主题的 Activity | 视觉上类似，但微信会 onPause，按返回要处理回栈 | 中高（要解决 MainActivity 复用、app-lock 绕过、WebView 冷启动） | 无障碍即可（已有） | 高：小米默认禁止"后台弹出界面"，即使无障碍也可能被拦 |
| C. 继续 WebView 弹窗 + 修 bug | 只修 `loadOptions` 重试，弹窗仍在记账 APP 里 | 不满足"当场弹"诉求 | 极小 | 无 | 无 |

**推荐 A**。理由：
- 你要的"在微信支付页直接弹"，只有 A 能真正做到不切栈、不打断对方 APP。
- B 在小米上坑最多（后台 Activity 启动限制、app-lock、WebView 冷启动白屏），后期排错成本高。
- C 只修 bug，不解决你说的核心诉求。

### 3.2 整体架构

```
微信/支付宝前台
    │
    │  ① 无障碍服务 onAccessibilityEvent（已有）
    ▼
PaymentAccessibilityService
    │  ② 解析出 CapturedPaymentInfo（已有）
    ▼
CaptureQueueDao.insert(entity)（已有，Room）
    │
    ├───► PaymentCapturePlugin.notifyCandidate（旧路径：WebView 弹窗，保留作为兜底）
    │
    └───► OverlayEntryManager.showOverlay(entity)   ★ 新增
              │
              │  ③ 检查悬浮窗权限
              ▼
        WindowManager.addView() 从底部滑入
        QuickEntryOverlayView（原生 Kotlin View）
              │
              │  ④ 用户点「记一笔」
              ▼
        OverlayEntryManager.commit(entity, categoryId, accountId)
              │
              │  ⑤ 不切回前台，拉起一个透明 Service/Activity
              │     调 FinanceBridge.commitExpense()
              ▼
        直接写 Capacitor SQLite 正式账本（同进程，复用现有 DB 连接）
              │
              │  ⑥ Toast 反馈 + 收起悬浮窗
              ▼
        用户还在微信支付页
```

### 3.3 关键新增组件

#### 3.3.1 Manifest 与权限

`AndroidManifest.xml` 加：

```xml
<uses-permission android:name="android.permission.SYSTEM_ALERT_WINDOW" />
```

运行时检查 `Settings.canDrawOverlays(context)`，没授权就跳 `Settings.ACTION_MANAGE_OVERLAY_PERMISSION`。这个权限和无障碍一样，Shizuku 可以代开（复用现有 `AccessibilityEnabler` 思路，发 `appops` 命令）。

#### 3.3.2 `OverlayEntryManager`（新增 Kotlin 单例）

位置：`capture/overlay/OverlayEntryManager.kt`

职责：
- `showOverlay(entity: CaptureQueueEntity)`：检查权限 → 构造 `QuickEntryOverlayView` → `WindowManager.addView`，LayoutParam 用 `TYPE_APPLICATION_OVERLAY`，宽度 MATCH_PARENT，高度 wrap_content，放屏幕底部。
- `dismissOverlay()`：`removeView`。
- `commit(entity, categoryId, accountId)`：收起悬浮窗 → 调 `FinanceBridge.commitExpense(...)` → Toast。
- 冷却期：复用现有 `INSERT_COOLDOWN_MS`，避免同一支付页重复弹。

#### 3.3.3 `QuickEntryOverlayView`（原生卡片 UI）

用 Kotlin 传统 View（或 Compose，但这个项目原生是 Java，建议继续 Java/View 风格保持一致）写一个紧凑底部卡片：

- 顶部：大字号金额（等宽数字，跟现有 `MoneyText` 同字号 30sp）+ 商户名
- 标签行：来源 tag（微信/支付宝）+ 建议分类 tag
- 分类区：横向 RecyclerView，5 个常用分类图标（从 Room 里按用户最近选择排）
- 账户区：横向 RecyclerView，4 个常用账户
- 底部：[忽略] [✓ 记一笔]
- 圆角 20dp、顶部拖拽条、半透明遮罩点外部关闭
- 主题色直接读现有 `colors.xml`，不用重新设计

**这部分不加载 WebView，所以启动是毫秒级，不闪屏。**

#### 3.3.4 `FinanceBridge`（新增：原生直接写正式账本）

这是最关键也最需要小心的一块。

现状：正式账本跑在 `@capacitor-community/sqlite`（WebView 里）。原生层不能直接调 JS。

方案：
- 在原生层新建 `FinanceBridge.java`，它持有一个**跟 Capacitor SQLite 同一个数据库文件**的原生 `SQLiteDatabase` 连接（因为是同进程，不会有跨进程锁问题；只要 WebView 那边暂时不写就行，单写者场景用 `BEGIN IMMEDIATE` 事务即可）。
- 暴露 `commitExpense(ledgerId, amountMinor, accountId, categoryId, occurredAt, merchant)` 方法，内部直接执行 INSERT 语句——**SQL 语句和字段名要跟前端 `finance-service` 里 `createExpense` 完全对齐**（这个要去读一下现有 migration SQL，照搬表结构）。
- 写完后通过 `PaymentCapture.acknowledgeEvents` 把 Room 队列那条标记掉。
- 最后发一个 `paymentCaptureCandidate` 空事件给前端，告诉它"账本数据变了，刷新首页列表"。

**风险与对策**：
- SQLCipher 加密：如果正式账本是加密的，原生层要用同一个 passphrase 打开。passphrase 现在存在 Android Keystore 里，原生层能拿到（因为是同一个 APP 进程）。这一步要先读一下 `@capacitor-community/sqlite` 的初始化代码确认。
- 如果对接成本太高，**退一步**：悬浮窗只做"预选分类+账户"，点确认后把选择写回 Room，然后用一个透明 Activity（Theme.NoDisplay）瞬间拉起 MainActivity 执行 `createExpense`，用户视觉上只看到一个 Toast。这个 Activity 100ms 内 finish，感知很弱。这个退路要写在方案里，作为 Plan B。

#### 3.3.5 触发点改造

`PaymentAccessibilityService.writeToQueue()` 在 `notifyCandidate / notifyQuickEntry` 之后加一行：

```java
// 旧路径保留：如果用户在记账 APP 前台，仍然弹 WebView 弹窗
PaymentCapturePlugin.notifyCandidate(entity);

// 新路径：如果不在前台，且有悬浮窗权限，弹原生悬浮窗
OverlayEntryManager.maybeShowOverlay(entity, isForegroundPackage());
```

`maybeShowOverlay` 内部判断：
- 如果当前前台 APP 就是我们自己（`getContext().getPackageName()`），不弹悬浮窗，走旧 WebView 路径。
- 如果是微信/支付宝/淘宝等白名单 APP，且 `Settings.canDrawOverlays()` 为 true，弹悬浮窗。
- 通知监听路径（`PaymentNotificationListenerService`）同理加一行。

### 3.4 顺手要修的 bug

不管做不做悬浮窗，下面这个 bug 都要修，它直接导致你"只能取消"：

**`capture-entry.ts:loadOptions` 失败后不重试。**

改法：
- 监听 `appStore.ledgerId` 变化，一旦从空变成有值，自动重新 `loadOptions`。
- `loadOptions` 加 3 次指数退避重试（100ms / 300ms / 800ms）。
- 分类/账户加载失败时，弹窗上不要静默空白，要显示"正在加载…"骨架屏，让用户知道不是坏了。

## 4. 分期实施建议

### 阶段 1：修 bug + 悬浮窗权限打通（0.5 天）

- Shizuku 代开悬浮窗权限（appops 命令）。
- **验收**：切回 APP 后弹窗不再只有金额，分类/账户能正常加载，能点确认入账。

### 阶段 2：原生悬浮窗 MVP（2-3 天）
- `OverlayEntryManager` + `QuickEntryOverlayView`（先做静态 UI：金额、商户、固定 5 分类、固定 4 账户、两个按钮）。
- 点击事件先用 `Toast` 占位，不真正写账。
- **验收**：微信支付成功后，悬浮窗从底部弹出来；忽略/关闭按钮正常工作；不打断微信。

### 阶段 3：接通入账（1-2 天）
- 实现 `FinanceBridge.commitExpense`（先试 Plan B：透明 Activity 拉起 MainActivity 入账；如果太绕再做原生直写）。
- 分类/账户按用户历史记录动态排序（最近用的排前面）。
- **验收**：微信支付成功 → 选分类 → 点确认 → Toast 提示 → 回到记账 APP 首页能看到这条账。

### 阶段 4：体验打磨（1 天）
- 金额可在悬浮窗里直接改（长按金额弹出数字键盘）。
- 商户名可改。
- 冷却期、去重、退款/转账的特殊处理（现在悬浮窗默认按"支出"入账，红包/转账要识别后走不同 UI）。
- 小米 HyperOS 实测：锁屏、后台清理、自启动、省电策略。

## 5. 风险与注意事项

1. **小米/HyperOS 权限链**：悬浮窗权限 + 无障碍 + 自启动 + 后台弹出界面，四个开关要在设置页一次性引导用户开完，每个都给"去开启"按钮。Shizuku 已就绪，能帮开其中两个。
2. **不要替用户点支付按钮**：悬浮窗只读取，不操作微信/支付宝 UI。这是技术基线文档里定的隐私底线，继续保留。
3. **多数据库写入冲突**：原生 `FinanceBridge` 和 WebView SQLite 同时写一个库，必须加锁。建议悬浮窗入账时短暂阻塞 WebView 写入（用一个全局 `ReentrantLock`），写完立刻释放。
4. **识别准确性**：悬浮窗里的分类/账户预选错了很正常，必须允许用户一键改。金额错了也要能改——识别错了比没识别还糟糕。
5. **隐私**：悬浮窗里不要显示银行卡号、支付密码等敏感信息；Toast 里也只显示"已记账 ¥xx"，不显示商户全称。
6. **不破坏现有 JSON 剪贴板流程**：你现在用豆包截图→JSON→剪贴板→自动入账的流程很好用，悬浮窗是新增通道，不动它。

## 6. 需要你拍板的两个问题

1. **入账路径选哪条**？
   - **方案 A（推荐）**：原生 `FinanceBridge` 直接写 SQLite，体验最丝滑，但要处理加密 DB 连接和 SQL 对齐，工程量稍大。
   - **方案 B（退路）**：悬浮窗收集选择后，用透明 Activity 拉起 MainActivity 完成入账，工程简单但会有一瞬间的"闪一下"。
   - 我建议先按 B 做通端到端，再换成 A。

2. **淘宝订单/电商场景要不要一起做**？
   - 微信/支付宝是支付成功页，识别规则成熟。
   - 淘宝是"下单成功"页，没有"支付成功"那种固定文案，且淘宝页面改版频繁，适配器容易失效。
   - 建议一期只做微信+支付宝，淘宝先用你现在的"截图给豆包→JSON 剪贴板"流程兜底。
