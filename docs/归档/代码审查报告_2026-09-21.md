## 0. 结论摘要（给只有三分钟的人）

这个 App 的底子相当好：整数分记账、复式记账断言、幂等迁移、SQLite 执行器抽象、设计 token 系统，这些都做对了。日常功能能用得起来不是运气，是这些约束在撑着。

但有 **13 个 P0 级别的问题**，其中一半你自己用着根本不会察觉，因为它们只在特定条件下发作：

**最该立刻看的四件事：**

1. **支付自动捕获这条管线，三条通道在 UI 上全部空转。** Room 数据库没开 `allowMainThreadQueries`，插件的所有 DB 访问都跑在 JS 桥主线程上——数据写进了库，但「待确认账单」永远是空的，「确认入账」永远报成功，自检界面直接把 Room 的英文异常甩给你。一行代码能救活。
2. **无障碍服务的核心能力被一行代码抹掉了。** `setServiceInfo()` 传了一个 `new` 出来的空对象，manifest 里声明的 `android:canRetrieveWindowContent="true"` 被整体覆盖，`getRootInActiveWindow()` 因此拿不到根节点。注释里写「先尝试完整 flags，失败降级」，但真正的问题不是 flags。
3. **`formatMinorToCny(-3155)` 返回 `"-32"`，正确值是 `-31.55`。** 负数金额的分位被 `%` 运算连同符号一起丢掉。这个函数被 6 处调用，全部金额展示都受影响。
4. **信用卡返现、优惠减免这些收入，在仪表盘上被当成「支出的减少」。** `createCreditIncome` 造的是 `type='refund'` 的交易却配 `income` 分类，而仪表盘 SQL 把 `refund` 统一当作 `-amount_minor`。结果就是：一笔 ¥300 的信用卡返现，仪表盘算成支出减 300，明细页显示收入 +300，两边说法完全不同。

**关于你问的「手搓组件」**：手搓本身没有任何问题，你的直觉是对的——问题不在「要不要手搓」，而在于**有三个系统性的失败**让风格匹配这件事落不了地：`tokens.css` 里定义的 token 和组件里实际引用的 token 几乎不重叠（`--color-primary` 定义了 0 次却引用了 17 次），`DeleteVerifyPopup` 里一个不带 `scoped` 的 `<style>` 用 `* { box-shadow: none !important; }` 把**全站所有阴影**干掉了，还有一个原生 `<select>`/`<input type="date">` 混在 Vant 体系里。手搓了 40 多个组件不是问题，**没有一个组件在用 token** 才是问题。具体该保留哪些、该迁移哪些、该删哪些，见 6.3 节，已经逐个给出判断。

**修复排期建议**在第 10 节，分四批，第一批（约 1 小时）能修掉捕获管线空转、负数金额、无障碍降级、系统设置被覆写这四件事。

## 2. 数据安全与隐私（P0）

### P0-1：生产环境默认 DEBUG 日志级别

`src/features/debug/app-logger.ts:67`：

```ts
const defaultConfig = (): LogConfig => ({ ...DEV_DEFAULT_CONFIG })
```

`PRODUCTION_DEFAULT_CONFIG` 定义在 `:44-49`，但**从未被自动套用**，也没有 `import.meta.env.PROD` 判断。当前生产构建跑的就是 DEBUG 级别。

**已经落到日志里的敏感内容：**

- `src/App.vue:171-176`：记录剪贴板内容的 `head: value.slice(0, 80)`。这个值是你从第三方 AI 工具复制的交易 JSON，可能含卡号。
- `src/App.vue:280-284`：记录 `amountMinor` / `merchant` / `method`。
- `src/services/finance-service.ts:792 / 839 / 947 / 1033 / 1068 / 1115 / 1148 / 1192 / 1240`：记录 `borrower` / `lender` / `amountMinor`，共 9 处。

**更关键的是这两条日志能被导出去。** `src/views/LogView.vue:123-143` 导出到 `ExternalStorage/Download`，`:181-215` 走系统分享面板。DEBUG 级别 + 一键导出 = 完整财务流水可分享出去。

**确认做对了的地方**：PIN 码**没有**被记录进任何日志。这一点值得记一笔，因为同类 App 经常犯这个错。

**改法**：

```ts
const defaultConfig = (): LogConfig =>
  import.meta.env.PROD ? { ...PRODUCTION_DEFAULT_CONFIG } : { ...DEV_DEFAULT_CONFIG }
```

同时把 `App.vue` 剪贴板那条改成只记 `length` 和指纹。

### P0-2：备份文件明文存储，且与 PIN 完全脱钩

`src/features/backup/backup-service.ts:107-109`：

```ts

```

### P0-3：PIN 方案偏弱，且「关闭锁定」不需要 PIN

`src/views/PinSetupView.vue:186` 和 `src/views/PinUnlockView.vue:41` 都是 `<PinPad :length="4" />`，但 `src/features/security/app-lock-service.ts:96-100` 允许 4-8 位。UI 把强度上限锁死在 4 位。

## 3. 金额与时间正确性（P0）

### P0-5：负数金额格式化错误 —— `formatMinorToCny(-3155)` 返回 `-32`

`src/domain/money.ts:17-21`：

```ts
export function formatMinorToCny(minor: number): string {
  const yuan = Math.floor(minor / 100)
  const cents = minor % 100            // JS 的 % 保留符号：-3155 % 100 === -55
  return cents > 0 ? `${yuan}.${String(cents).padStart(2, '0')}` : String(yuan)
}
```

**实测结果**：

| 输入（分） | 实际输出 | 正确值 |
|---|---|---|
| `-3155` | `-32` | `-31.55` |
| `-50` | `-1` | `-0.50` |
| `-100` | `-1` | `-1`（碰巧对，cents 为 0） |
| `-105` | `-2` | `-1.05` |

`cents > 0` 这个判断在负数时**永远为假**（`-55 > 0` 是 false），所以小数部分整个被丢掉，`yuan` 又被 `Math.floor` 向下取整——两头都错，加起来差得离谱。

**调用点**（6 处，覆盖全部金额展示路径）：`components/AccountPicker.vue:129` / `:157`、`components/CaptureQuickEntrySheet.vue:122`、`components/RecordSheet.vue:971` / `:1001`、`views/CaptureInboxView.vue:317`。

**改法**：

```ts
export function formatMinorToCny(minor: number): string {
  const negative = minor < 0
  const abs = Math.abs(minor)
  const body = `${Math.floor(abs / 100)}.${String(abs % 100).padStart(2, '0')}`.replace(/\.00$/, '')
  return (negative ? '-' : '') + body
}
```

这是本次审查中**性价比最高的一处修复**：一行逻辑改动，修好全站所有负数金额展示。

### P0-6：`type='refund'` 双重语义 —— 信用卡返现在仪表盘上被当成「支出减少」

`src/domain/accounting.ts:191`，`createCreditIncome`：

```ts
export function createCreditIncome(command: CreditIncomeCommand): TransactionDraft {
  assertAccount(command.liabilityAccount, 'credit', 'liabilityAccount')
  assertCategory(command.category, 'income')          // ← 收入分类
  return createDraft('refund', command, [              // ← 但 type 是 refund
    accountEntry(command.liabilityAccount.id, 'debit', command.amountMinor),
    categoryEntry(command.category.id, 'credit', command.amountMinor),
  ])
}
```

从复式记账看，这一笔**确实是收入**（负债借方减少 + 收入分类贷方增加），`assertBalanced` 也通过了。但 `type` 字段写的是 `refund`，然后三处查询把它当成支出：

- `db/repositories/dashboard-repository.ts:61-63`：`WHEN type = 'refund' THEN -amount_minor`
- `db/repositories/dashboard-repository.ts:81-87`：同上模式
- `db/repositories/statistics-repository.ts:111-112`：同上

**后果**：一笔 ¥300 的信用卡返现 → 仪表盘算成「支出 -300」（即支出减少），收入统计里完全看不到这笔钱；用户配了一个收入分类，但分类统计页面显示不出来。所有因优惠产生的收入（返现、积分抵扣、免息优惠）**在仪表盘上整体隐形**。

**同一个数据行，两处界面说法相反**（核实时额外确认）：

`src/components/TransactionDetailSheet.vue:35-47`：

```ts
const displayAmount = computed(() => {
  if (tx.value.type === 'expense' || tx.value.type === 'credit_purchase') {
    return -tx.value.amountMinor
  }
  return tx.value.amountMinor          // refund 落在这里 → 正数
})

const amountTone = computed(() => {
  if (tx.value.type === 'income' || tx.value.type === 'refund') return 'income'  // 绿色
  ...
})
```

明细页把 `refund` 显示成**绿色的 +300 收入**，仪表盘把它算成**支出的减少**。同一个数字，两种财务含义。

**改法**：把 `createCreditIncome` 的 type 改成 `income`，并在迁移里把历史 `refund` 中「配了 income 分类」的记录修正过来；仪表盘和统计那三条 `WHEN type='refund'` 的分支保留给真正的退款场景（配 expense 分类的）。**注意**：这里必须区分两种语义，不能一律改，否则真正的退款会被当成收入。

### P0-7：写入路径的 UTC 归一化不对称

`src/db/repositories/transaction-repository.ts`：

```ts
const occurredAt = toUtcIso(draft.occurredAt)    // :156  创建路径：归一化
setClauses.unshift('occurred_at = ?')             // :357  更新路径：直接写原始值
```

**创建时归一化成 UTC，更新时写原始值。** `src/services/finance-service.ts` 里有 **0 处** `toUtcIso` 调用。

`occurred_at` 是 `date(...)`/`date_part(...)` 这类 SQL 时间函数的输入。同一条记录，被改过一次之后，它的时区表示就和从没被改过的记录不一样了。这个 bug 平时不发作，一旦有人编辑一笔交易，它当天的日切归属就可能变。

**改法**：`edit` 路径同样走 `toUtcIso`；再补一条断言测试：创建后更新、`occurred_at` 字符串不变。

### P0-8：两套并存的时间分桶方式 —— SQL `localtime` vs JS 前缀切片

这是最阴的一个：`finance-service.ts:1572` 的 `localMonthUtcRange` **本身是对的**（我实际跑了 6 个边界用例验证，见第 11 节纠错记录 3），但它造出的 UTC 时间窗，和另外十几个地方用字符串前缀切出来的「月份」，是两套完全不同的规则。

**SQL 侧（按本地时间分桶，正确）—— 只有 2 处**：

```sql
-- db/repositories/dashboard-repository.ts:59 和 :66
date(occurred_at, 'localtime')
```

**JS 侧（直接对 UTC 字符串切前缀）—— 14 处**：

| 位置 | 写法 |
|---|---|
| `views/BillsView.vue:89` | `item.occurredAt.slice(0, 10)` |
| `views/AccountStatisticsView.vue:44` / `:126` | `.startsWith(selectedMonth)` |
| `views/CategoryStatisticsView.vue:46` / `:140` | `.startsWith(selectedMonth)` |
| `views/AccountDetailView.vue:111` | `.slice(0, 7)` |
| `services/statistics-service.ts:120` / `:168` | `.slice(0, 7)` |
| `features/export/export-service.ts:156` | `.slice(0, 10)` |
| `features/credit/credit-cycle.ts:42` | UTC 前缀 |
| `db/repositories/reminder-repository.ts:150`、`services/reminder-service.ts:169`、`views/RemindersView.vue:255` | 同 |
| `views/PayablesView.vue:235`、`views/ReceivablesView.vue:235`、`views/TemplatesView.vue:318` | 同 |

`occurred_at` 存的是 **UTC** ISO 字符串。对 UTC 字符串切前 7 个字符，得到的是 **UTC 月份**，不是本地月份。

**后果**：在 UTC+8 时区，本地时间 00:00–07:59 的交易属于**昨天/上个月**。你一笔本地 5 月 1 日 07:30 的支出：

- 首页仪表盘（SQL localtime）：算 5 月 1 日 ✓
- `BillsView`（`slice(0,10)`）：算 4 月 30 日 ✗
- `AccountStatisticsView`（`startsWith('2024-05')`）：算 4 月 30 日 ✗

同一笔交易，在
__zcode_status=$?
if [ "$__zcode_status" -eq 0 ]; then pwd -P > '/c/Users/lemon/AppData/Local/Temp/zcode-dea0bf4e-352d-4a8a-b8ba-c48b0116653e-cwd'; fi
exit "$__zcode_status"
不同页面属于不同月份。而且它只在「凌晨 0–8 点之间花的钱」上发作——大多数人记账习惯在白天，所以用了 40 多天没暴露。

**改法**：把分桶统一到 SQL 侧（`date(occurred_at,'localtime')` 下推到查询里），或者统一到一个 `localDateOf(iso)` 工具函数，然后 14 处 JS 全部替换掉。**不要两套并存。**

## 4. 数据丢失风险（P0）

### P0-10：备份包里缺某张表 = 那张表被清空

`src/features/backup/backup-repository.ts:289`：

```ts
const rows = data[schema.name] ?? []      // 缺表 → 空数组 → replaceAll 清空
```

### P1-14：外键约束依赖隐式副作用（已核实：当前是 ON 的）

**先说结论**：有审查意见称「外键约束在运行时处于关闭状态」——**这是错的，外键当前是开启的**，我逐层验证过：

- `PRAGMA foreign_keys = ON` 写在 `src/db/migrations/migration-runner.ts:9`，位于 `MIGRATION_TABLE_SQL` 常量内
- `runMigrations` 启动时会先执行这个 SQL
- `src/db/bootstrap.ts:52` `connection.open()` → `:67` `runMigrations`
- 连接是单例：`connectionPromise ??= createConnection()`（`:163`）
- `CapacitorSqliteExecutor` 把全部操作路由到同一个 `SQLiteDBConnection`
- `PRAGMA foreign_keys` 是**连接级别**的设置，不是事务级别
- `splitByPragma` 会把 pragma 从事务块中拆出来单独执行

所以约束确实在生效。**真正的问题不是「现在是关的」，而是「它是通过『迁移跑过了』这个副作用间接生效的」**——没有任何断言、没有测试，未来任何新增一条「直接新建连接」的代码路径都会静默丢掉约束。

**改法**：在 `createConnection()` 之后**显式**再执行一次 `PRAGMA foreign_keys = ON`（不依赖迁移路径），加一条断言测试 `PRAGMA foreign_keys` 返回 1。

## 11. 附录：本次审查的纠错记录

审查过程中有**三条被提出但经我复核后证伪**的结论。这里如实记录，因为它们如果没被发现，会浪费你大量时间去做根本不存在的修复。

### 纠错 1：「外键约束在运行时处于关闭状态」 —— 错误，当前是开启的

**验证过程**：
- `PRAGMA foreign_keys = ON` 位于 `migration-runner.ts:9`，在 `MIGRATION_TABLE_SQL` 常量内
- `runMigrations` 启动即执行
- `bootstrap.ts:52` `open()` → `:67` `runMigrations`
- 连接是单例（`connectionPromise ??= createConnection()`，`:163`），`CapacitorSqliteExecutor` 全部走同一连接
- `PRAGMA foreign_keys` 是**连接级**设置，`splitByPragma` 把 pragma 从事务中拆出单独执行

**真实问题**（已改为 P1-14）：它生效是「迁移跑过了」这个副作用的间接结果，无断言、无测试，未来任何新开一条连接路径都会静默丢掉约束。

### 纠错 2：「恢复旧版本备份会重放建表式迁移，静默丢列或启动锁死」 —— 过于严重

**验证过程**：`BACKUP_TABLES[0] === 'schema_migrations'`（`backup-types.ts:13`）。备份自带自己的迁移状态表，表结构与记录自洽，还原后走正常升级路径。

**保留的真实风险**（已拆成独立条目）：P0-10 缺表即清空、P0-12 元数据谎报 schema 版本、以及「还原后不触发重新迁移」这个单独的问题。

### 纠错 3：「`localMonthUtcRange` 有 8 小时边界 bug」 —— 错误，实测 6 个边界用例全部正确

**验证过程**：把 `finance-service.ts:1572` 的原函数在 node 里实跑（时区设为 UTC+8，以 2024 年 5 月为例）：

```
查询窗口 startUtc = 2024-04-30T16:00:00.000Z
查询窗口 endUtc   = 2024-05-31T16:00:00.000Z

本地 4/30 23:50  →  2024-04-30T15:50:00.000Z  → 不计入 5 月  ✓
本地 5/1  00:10  →  2024-04-30T16:10:00.000Z  → 计入 5 月    ✓
本地 5/1  07:30  →  2024-04-30T23:30:00.000Z  → 计入 5 月    ✓
本地 5/31 23:30  →  2024-05-31T15:30:00.000Z  → 计入 5 月    ✓
本地 6/1  00:10  →  2024-05-31T16:10:00.000Z  → 不计入 5 月  ✓
本地 6/1  07:50  →  2024-05-31T23:50:00.000Z  → 不计入 5 月  ✓
```

原结论的推理有一步算反了：它写「`< endUtc` 不成立」，却得出「被错误包含进 5 月」——比较关系的结论方向反了。

**保留的真实问题**（已改为 P0-8）：这个时间窗构造函数本身没错，**问题在于另外 14 处 JS 用 UTC 字符串前缀切片分桶，和这 2 处 SQL `date(occurred_at,'localtime')` 是两套并存的方法**。同一笔凌晨的交易在不同页面属于不同月份。
