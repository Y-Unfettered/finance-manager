## 0. 结论摘要（先看这一页）

自评完成度 70%–80% 是准确的：**记账主链路（捕获 → 确认入账 → 备份恢复）已经可用**，真正拖后腿的不是功能，而是两类东西：

1. **分类体系还没"成体系"**：图标库只有 52 组、颜色是自由 hex 且默认写死蓝色、统计图不用分类色。这直接限制了"后续按细分分类分析个人消费"的目标。
2. **界面节奏没成体系**：间距、行高、安全区、弹层关闭契约各页各写一套，出现了"两张卡片贴在一起""文案和链接隔 20px"这类割裂感。

本轮确认的缺陷里，**最关键的两条都能在代码里闭环，不是偶发**：

| 编号 | 缺陷 | 结论 |
|---|---|---|
| BUG-01 | 停用分类的确认弹窗点完不关闭、二次弹窗名字为空 | **确定性缺陷**：确认后从未把 `showArchiveConfirm` 置 false，同时把 `pendingArchive` 清空，于是弹窗常驻且文案变空。账本归档页有同构问题。 |
| BUG-03 | 账户统计"支出分类"条形图只有绿条和金额、没有分类名 | **确定性缺陷**：ECharts `grid.left = 0` + `containLabel: false`，类目轴标签被画到画布外裁掉。 |

"取消后偶发无法上下滚动"目前**无法从代码直接断定**（今天也复现不了），本 PRD 给出 3 条假设 + 取证方案 + 架构级建议（统一滚动锁），不猜结论。

四条需求主线：

- **需求一**：分类体系 2.0 —— 图标库扩容到能覆盖"购物/交通/娱乐"等细分，配色改为主题色驱动的语义色槽。
- **需求二**：统计页统一"年份滚轮"——横向滚动、两侧渐隐、中间吸附，分类统计与账户统计同款。
- **需求三**：诊断日志保留最近 3 个自然日，滚动淘汰。
- **需求四**：UI 体系化规整 —— 间距、行高、卡片容器、安全区、弹层契约、Token 完整性。

## 1. 背景与目标

### 1.1 用户背景

- 单人自用账本，本地优先，不连云账户；已完成自动记账链路（无障碍捕获 → 待确认 → 入账）。
- 目前处于"完成度够用、但要长期用下去"的阶段，用户开始在意：分类能不能分得更细、视觉是不是成体系、出问题时能不能查到日志。
- 决策层级：这一版是"自我打磨"，不是上架版本；但方案要经得起以后上架/上 Google Play 的审视（渠道决策仍未定）。

### 1.2 本轮目标（Goal）

| 编号 | 目标 | 可衡量结果 |
|---|---|---|
| G1 | 分类体系能承载"细分二级分类" | 新建二级分类时，购物/交通/娱乐等常见子类都能找到语义贴切的图标；配色随主题自动统一 |
| G2 | 统计页时间筛选体验统一、耐看 | 分类统计与账户统计使用同一套年份滚轮；滑动/吸附/渐隐表现一致 |
| G3 | 出问题能查、能追 | 杀掉进程重开仍能看到近 3 天日志；第 4 天自动淘汰第 1 天 |
| G4 | 界面节奏可预期 | 同层级卡片间距、行高、区块间距在同一套 Token 下取值；设置页不再出现 0 间距/20px 空档 |
| G5 | 归档类操作不再"卡住" | 确认后弹窗必关、失败必提示、页面必可滚动 |

### 1.3 非目标（Non-goal）

- 不改记账核心事务、金额口径（`amount_minor` 整数分）、余额聚合视图。
- 不改自动记账的捕获链路（无障碍服务、Shizuku、读屏规则）。
- 不引入三级分类（当前模型明确"最多两级"，见 `finance-service.ts:520`）。
- 不做深色模式的重新设计（沿用现有 `data-theme` 变量映射）。
- **本轮不提交任何代码改动**；PRD 只用于评审与排期。

## 3. 缺陷清单（问题发现）

> 分级：P0 = 数据/交互阻断，P1 = 明显体验缺陷，P2 = 一致性欠账。

### BUG-01 [P0] 停用分类：确认后弹窗不关闭，二次弹窗分类名为空

**用户现象**
1. 分类管理里点某分类的"停用"，弹出"停用该分类？"，标题/描述正常（带分类名）。
2. 点"停用"确认后，系统"卡住"：弹窗不消失，看起来还能点但点了没反应，只能点"取消"退出。
3. 退出后再点一次"停用"，新弹窗括号里**空着**（`停用「」后不可再选它记账…`）。
4. 账本页的"归档账本"有同样表现。

**根因链（确定性）**
1. `setArchived(item, true)` → `showArchiveConfirm = true`、`pendingArchive = item`（`CategoryManagementView.vue:169-177`）。
2. 弹窗 `@confirm="pendingArchive && doSetArchived(pendingArchive, true)"`（`:426-434`）。
3. `doSetArchived` 的 `finally` 只做两件事：`archiving = false`、`pendingArchive = null`（`:179-190`）。**全程没有把 `showArchiveConfirm` 置为 false**，而 `AppConfirmPopup` 本身也没有"确认后自动关闭"的契约（`AppConfirmPopup.vue:52` 只 `emit('confirm')`）。
4. 于是：弹窗仍在；描述模板 `停用「${pendingArchive?.name ?? ''}」…` 因为 `pendingArchive` 已为 null → 名称变空。
5. 再点确认按钮：处理器 `pendingArchive && …` 短路，什么都不执行；`loading` 已恢复 false，按钮看起来可点。**唯一出口只剩"取消"。**
6. 补充：`doSetArchived` 没有 `catch`。若 `archiveCategory` 或 `load()` 抛错，错误被吞在事件处理器里，弹窗同样不关、也没有任何错误提示。

**同构缺陷**：`LedgerView.vue:81-98`（`doToggleArchive`）+ `:152-160`（弹窗）完全同样的写法——归档账本也会卡住、名称变空。

**修复要求（后续实施时）**
- `AppConfirmPopup` 增加明确契约：确认后默认关闭（`autoClose` 默认 true）；异步确认期间保持 `loading`，**禁止重复提交**；失败时保留弹窗并展示错误文案（需要新增 `error` 插槽/属性）。
- 页面侧不再各自管理关闭状态；`pendingArchive` 只在"弹窗已关闭"之后清空，避免出现空文案。
- 归档失败要有可见反馈（Toast 或弹窗内红字），不能静默。

**验收标准**
- 点"停用"→确认→弹窗 200ms 内关闭，列表显示"已停用"，页面可正常上下滚动。
- 连续归档 5 个分类，不出现残留弹窗、不出现空名文案。
- 人为制造失败（如断库/抛错）时，弹窗保留并显示错误原因，取消可退出。
- 账本归档同标准通过。

### BUG-02 [P0] 点"取消"退出后，偶发整页无法上下滚动

**用户现象**：偶发；今天复测未复现。表现是"页面完全不跟手"，只能杀掉重开。

**为什么本 PRD 不给单一结论**：代码里没有一条能 100% 推出该现象的路径，需要取证。以下是三条按可能性排序的假设，均附可验证点。

**假设 A（最可能，可与 BUG-01 合并解释）：全屏遮罩吃掉触摸**
- `AppConfirmPopup` 的遮罩是 `position:fixed; inset:0; z-index:1000`（`AppConfirmPopup.vue:64-73`）。在 BUG-01 状态下它一直挂着，页面当然"不能滚"——这解释了"卡住"期间的现象。
- 需要验证的是"取消之后"是否仍有残留节点/遮罩：`Transition` 是 180ms opacity，理论上会移除；但若 leave 被打断（快速切页、KeepAlive 失活、路由过渡同时发生），需实测确认。

**假设 B：Vant Popup 的滚动锁计数泄漏**
- `AppBottomSheet` 用 Vant `Popup`，默认 `lock-scroll=true`。Vant 的锁是加在 `document.body` 上并对 document 的 `touchmove` 做拦截（允许弹层内部滚动）。
- 而本 App 真正的滚动容器是 `.route-page-frame`（`App.vue:534-554`），不是 body。**锁的对象和实际滚动的对象不是同一个**。
- 一旦 unlock 没配对（嵌套弹层、页面失活时 `visible` 反复切换、弹层在 show=true 状态下被销毁），body 上的 `van-overflow-hidden` 与 touchmove 拦截会残留，表现就是"整页不跟手"。
- 观察点：`AppBottomSheet.vue:23-31`（`visible = show && pageActive`，页面失活只隐藏、不重置 `show`）；`AppSelect.vue:69`（`sheetVisible` 同理）。返回页面后弹层可能"复活"，锁再次叠加。

- **假设 C（与 BUG-13 同源）：滚动位置恢复与内容变化打架** —— `RoutePageFrame` 在 `onActivated` 时全量恢复所有元素的 `scrollTop`（`RoutePageFrame.vue:52-73`），且 `nextTick` 后再写一次。归档成功后列表项变化，若恢复到旧位置而 `scrollHeight` 变小，会表现为"停在底部不动"或"位置莫名跳走"。

**取证计划（实施前先做，不改业务代码逻辑）**
1. 在诊断页（或设置→诊断的临时区块）展示实时状态：`document.body.className`、`body.style.overflow`、`.route-page-frame` 的 `scrollTop/scrollHeight/clientHeight`、`window.getComputedStyle(document.documentElement).overflow`。
2. 在归档流程 5 个节点打现有日志（tag 用 `category`）：打开弹窗 / 点确认 / 归档返回 / 列表刷新完成 / 弹窗关闭。
3. 复现脚本（真机，debug 包）：
   - 连续 5 次"停用 → 确认"；
   - "停用 → 确认 → 立刻切后台 → 回前台"；
   - 先打开编辑弹层 → 关闭 → 再归档；
   - 路由快速来回切 10 次后归档。
4. 判定标准：若残留时 `body.className` 含 `van-overflow-hidden`，即假设 B 成立；若遮罩节点仍在 DOM，即假设 A；若 `scrollTop` 异常而前两者正常，即假设 C。

**修复要求（架构级，治本）**
- 弹层统一使用自有的 `usePageScrollLock()`：锁 **`.route-page-frame`**（真实滚动容器），引用计数配对释放，页面失活/卸载时强制释放。
- Vant Popup 传 `:lock-scroll="false"`，不再依赖 body 锁。
- 所有 Teleport 到 body 的遮罩统一在 `onUnmounted`/`onDeactivated` 里兜底置 false。
- `AppSelect`/`AppBottomSheet` 在页面失活时应重置 `show`，避免返回后"弹层复活"。

**验收标准**
- 上述 4 个复现脚本各执行 10 轮，无一次出现滚动失效。
- 从任意弹层返回列表页，页面立即可滚动（触摸位移 > 0 时 `scrollTop` 同步变化）。

### BUG-03 [P1] 账户统计"支出分类"：只有绿条和金额，没有分类名

**现象**：图表里出现一根绿色横条，右侧写 `12.76`，不知道属于哪个分类。

**根因（确定性）**
- `DistributionBars.vue:35`：`grid: { left: 0, right: 50, top: 4, bottom: 4, containLabel: false }`。
- 类目轴 `yAxis` 的标签默认绘制在绘图区左侧，`left: 0` + `containLabel: false` 时标签坐标落在画布 x<0 区域，被 canvas 直接裁掉。
- 所以只剩"条 + 右侧数值"，数值的 `¥` 也可能因 `right: 50` 留白不足被裁。
- 另外：该图表没有标题外的单位说明、没有图例/占比，用户无法把条目和分类对上。

**修复要求**
- 改为 `containLabel: true`，或 `grid.left = 72~88px` 明确给标签让位；类目标签宽度自适应、超长省略但保留前 6 字。
- 右侧数值统一 `¥1,234.56` 千分位、右对齐，预留 ≥56px。
- 与环形图共用同一份"归并后"数据（见 BUG-04），保证环形图图例与条形图条目一一对应、同色。
- 补一条说明文案："支出 = 消费 − 退款，不含转账/还款"。

**验收标准**
- 每个条形左侧都有分类名；名称与环形图图例完全对应。
- 首屏（393dp 宽）下分类名不被裁切、金额不换行。

### BUG-04 [P1] 账户统计"支出分类"出现一堆 0 值/负值占位项

**根因**
- `statistics-repository.ts:71-88` 的 `accountDistribution` 按 `COALESCE(parent.id, categories.id)` 分组聚合，**没有 `HAVING amountMinor > 0`**。
- 只要某分类有交易参与（例如"消费 + 退款"净额为 0、或只有退款为负），就会产出一行 0/负值。
- 图表 `DistributionDonut` 内部会过滤 `amountMinor > 0`（`DistributionDonut.vue:41`），但 `DistributionBars` 不过滤 → 图例干净、条形图一堆 0 项，两处对不上。
- 账户统计页没有 `distribution.length > 1` 的保护（分类统计页有，`CategoryStatisticsView.vue:184`）。

**修复要求**
- 数据层：`HAVING amountMinor > 0`（或服务层统一过滤）；退款冲抵为 0 的分类不再出现在"支出分类"里。
- 展示层：按金额倒序，取前 8 个，其余合并为"其他"；占比 <1% 的并入"其他"；"其他" 用中性灰、固定最后一位。
- 账户统计与分类统计共用同一个 `buildDistribution()` 归一化函数，避免两页各写一套。
- 空数据：显示"该区间无支出"空状态，不渲染空图表。

**验收标准**
- 选"今年"查看任意账户，条形图条目数与环形图图例数一致，且无 0 值行。
- 只有退款、没有消费的分类不出现在列表中。
- 分类统计页同样口径（回归）。

### BUG-05 [P1] 设置 → 诊断：两张卡片间距为 0

**根因**
- `SettingsView.vue:285-318` 的"诊断"区块里，两个 `BaseCard` 是兄弟节点；`section` 本身没有 `display:grid/gap`（`SettingsView.vue:337` 的 `gap` 只作用于 `.content` 的 **section 之间**）。

- 结果：外观区块 12px、诊断区块 0px —— 同类结构两套间距，是"割裂感"的直接来源。

**修复要求**

- 卡片间距统一 12px；章节间距统一 20/24px（沿用 `--space-5/6`）。
- 清理各页散落的 `margin-top` 补丁（`appearance-entry` 等）。

**验收标准**
- 设置页 4 个区块内所有相邻卡片间距实测 12px（±0）。
- 代码里不再出现"靠 margin-top 补间距"的写法。

### BUG-06 [P1] "查看最近一次抓取结果"与上方文案间距过宽

**根因**

### BUG-13 [P2] 滚动位置恢复靠全量 DOM 遍历，且与自身"禁止 transform"的注释冲突

**事实 1：全量遍历恢复**
- `RoutePageFrame.vue:35-50` 的 `captureScrollPositions()` 对 `root.querySelectorAll('*')` 全量遍历，把每个"有滚动偏移或可滚"的元素都记进 `scrollPositions`。
- `:52-66` 再逐个写回，并在 `nextTick` 后又写一遍。
- 后果：
  - 分类管理页（40–60 行）每次进出都 O(n) 遍历两次、写回两次；
  - **内层滚动容器也被恢复**——图标选择器（`max-height: 246px` 可滚，`CategoryManagementView.vue:653`）、日志列表、弹层内列表，返回页面时会被强行拉回旧位置，用户观感是"列表自己跳了一下"。
- 这与 BUG-02 的假设 C 直接相关：滚动"看起来卡住"有时其实是"被恢复到了别处"。

**事实 2：注释与实现互相矛盾**
- `App.vue:544-546` 明确写着：**不要**给 `.route-page-frame` 常驻 `transform / will-change`，否则 fixed 子孙元素会相对内容定位。
- 但 `App.vue:556-558` 的 `.route-page-enter-active / .leave-active { will-change: transform }` 作用的正是同一个元素（`RoutePageFrame` 根节点就是 `.route-page-frame`，被 `<Transition name="route-page">` 包裹，`App.vue:493-503`）。
- 即：过渡的 260ms 窗口内，容器真的变成了 containing block，页面内**未 teleport 的 fixed 元素**（局部遮罩、浮动按钮、临时提示）会在这段时间里相对内容定位而错位。

**修复要求**
- 滚动恢复只处理"路由帧根节点 + 通过 provide 显式注册的滚动容器"，不做全量遍历；恢复失败或容器已被卸载时跳过，不写回。
- 路由过渡动画移到 `RoutePageFrame` 内的一层 wrapper 上（帧本身不参与 transform），或改为只做 opacity；无论如何，`will-change: transform` 不能落在滚动锚点上。

**验收标准**
- 来回切页 20 次，各页滚动位置一致；内层列表（图标选择器/日志）不被强行复位。
- 过渡期间对页面截图，无任何固定元素位移。

### 4.5 配色方案：从"自由 hex"改为"主题语义色槽"

**现状问题**（见 BUG-08）：自由取色 + hex 落库 + 默认蓝 + 统计图另用一套硬编码色。

**方案对比**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 全继承主题 | 所有图标统一用 `--color-primary-*` | 最统一、最省事 | 分类之间没有区分度，扫一眼看不出"餐饮/交通" |
| B 语义色槽（推荐） | 定义 8 个色槽 `--color-cat-1..8`，绿/蓝主题各一套；分类只选槽位，不选 hex | 有区分度 + 随主题自动变 + 可做统计配色 | 需要一次数据迁移（hex→槽名） |
| C 保留自由取色 | 现状 | 灵活 | 主题不一致、统计图仍脱钩、用户自述"不想自己调" |

**推荐 B**，具体规格：

- 色槽（两套主题各给 8 个同语义、可区分的色相）：
  `cat-1` 主题主色（餐饮/高频）、`cat-2` info 蓝（购物）、`cat-3` accent 金（居住/账单）、`cat-4` 珊瑚（娱乐/警示型消费）、`cat-5` 紫（人情/礼品）、`cat-6` 青绿（收入）、`cat-7` 中性灰（其他）、`cat-8` 棕（宠物/家居）。
- 数据存储：`categories.color` 存槽名（`cat-1`…`cat-8`），**不存 hex**；渲染时 `var(--color-cat-N)`。
- 兼容：加载到非槽名（历史 hex）时，按 HSL 色相就近映射到槽位（写一次迁移），或统一落到 `cat-1` 并允许用户重选。
- 编辑 UI：把 `<input type="color">` 换成 **8 个色块单选**（每块 44×44 触控，选中打勾），文案"跟随主题色，切换主题会自动适配"。
- 派生规则：图标底色 = `color-mix(in srgb, var(--color-cat-N) 12%, transparent)`（沿用现有 `CategoryIcon` 的 12% 逻辑），描边/文字 = 槽色本身。
- 一致性：`DistributionDonut` / `DistributionBars` 改为读取分类槽色；环形图最多 5 系列 + "其他"，同一分类全应用同色。
- 无障碍：色不是唯一编码（配文字/图标）；图标在 12% 底上对比度 ≥3:1；深色模式下槽色需单独校验（`data-theme='dark'` 下另给一套）。
- 约束：**不允许任意 hex**（避免再次脱钩）；如确有自定义需求，作为 P2 的"高级选项"另议。

**验收标准**
- 新建分类时只出现 8 个色块，无系统取色器。
- 切换"松石绿 ↔ 晴空蓝"后，分类管理页所有图标颜色随之变化，且 8 个槽在两种主题下都能互相区分。
- 统计页环形图/条形图颜色 = 该分类在分类管理页的颜色。

### 4.6 分类层级与归档规则

- 维持"最多两级"（`finance-service.ts:520` 已有约束），二级向上归集到一级做预算/统计。
- 归档（停用）语义需在 UI 上写清：不再可选记账、历史保留、可恢复；**一级归档时其二级一并不可选**（当前只过滤了自身，需明确规则并验证）。
- 二级分类的图标默认继承一级，但允许独立设置（当前已是该行为，需在 UI 明示）。

### 4.7 需求一验收清单

1. 图标库 ≥80 组，覆盖 4.3 表内全部建议项；搜索"内衣""箱包""家电""洗护""文具""手办""停车"均能命中。

## 5. 需求二：统计页统一"年份滚轮"

### 5.1 现状

## 6. 需求三：诊断日志保留最近 3 天（滚动淘汰）

### 6.1 现状（事实）

| 项 | 现状 | 影响 |
|---|---|---|
| 前端日志 | 只在 Pinia 内存（`app-logger.ts:121-141`） | 杀进程/重开即清零，无法回溯"昨天那次 bug" |
| 淘汰策略 | 按条数裁剪（2000/500） | 高频 tag（clipboard/nav）会把当天的关键错误挤掉 |
| 原生诊断 | 200 条内存 ring（`AccessibilityDiagnostics.java:38`） | 同上 |
| 原生导出文件 | 只写不删（`PaymentCapturePlugin.java:1252-1263`） | 目录会无限增长 |
| 清空 | `clear()` 直接清内存 | 无"只清今天"粒度 |

### 6.2 需求规格

**保留窗口**：保留 **最近 3 个自然日**（含今天）；第 4 天产生第一条日志时，淘汰最早那天全部记录。

- 例：1 号、2 号、3 号各有日志；4 号写入新日志 → 1 号整日清除；5 号写入 → 2 号清除。
- "自然日"按本地时区（Asia/Shanghai）切分，不按 24 小时滑窗。

**容量双闸**

| 闸门 | 规则 |
|---|---|
| 天 | 上限 3 天 |
| 条 | 每天 ≤ 800 条（warn/error 永不因条数被裁剪，只裁 debug/info） |
| 字节 | 全局 ≤ 2 MB；超限优先裁最旧那天的 debug/info |

**存储**

- 建议落 SQLite（项目已有 `@capacitor-community/sqlite`），新表：
  `app_logs(id INTEGER PK, day TEXT 'YYYY-MM-DD', ts INTEGER, level TEXT, tag TEXT, message TEXT, data_json TEXT)` + 索引 `(day)`、`(level)`。
- 迁移：新增 migration（不动历史表）；`backup-repository` 的 `TABLE_SCHEMAS` 是否需要纳入日志表 → **默认不纳入备份**（日志是诊断数据，不进备份包），需在 PRD 评审时确认。
- 写入节流：内存缓冲 + 800ms 批量 flush；页面切后台/退出前强制 flush；单条 `data_json` ≤ 1KB（超出截断并标注 `truncated`）。
- 读取：日志页默认只查"近 3 天"，按天分组（今天/昨天/前天）。

**UI 要求（设置 → 诊断 → 诊断日志）**

- 顶部摘要："最近 3 天 · 共 N 条 · 约 X KB"，并显示"保留至 2026-11-04"。
- 列表按日分组；组头显示日期 + 当日条数 + 当日 warn/error 数。
- 筛选保留现有级别/标签/关键词；新增"日期"筛选（3 天）。
- 清空：二次确认，文案写清"只清本机最近 3 天日志，不影响账本数据"。
- 导出：默认导出"近 3 天全部"；另给"仅导出今天"；文件名含日期范围 `app-log-20261104_20261106.json`。
- 导出前提示：日志可能包含金额、账户名等业务字段（本地文件，不上传），需用户确认。

**原生侧对齐**

- `AccessibilityDiagnostics` 的 ring 从 200 提升到"当日 + 前两日"的容量，并落文件/SQLite（与前端同一保留窗口）。
- `exportDiagnosticLog` 生成的 `diagnostic_*.json`：**只保留最近 5 个文件或最近 3 天**，超出的自动删除（当前是无限增长）。

### 6.3 不影响性能的硬约束

- 日志写入不得进入记账事务；不得阻塞 UI 线程（原生用后台线程）。
- 关闭开关（`config.enabled=false`）时零写入。
- 日志中的金额/账号：保留用于排查，但导出前提示；不得上传。

### 6.4 兼容

- 现有 `LogConfig`（enabled/maxEntries/globalMinLevel/tagMinLevels）字段保留，`maxEntries` 语义扩展为"每日上限"；老配置可平滑读取。
- 现有 `exportJson()` 结构保留 `entries` 字段，新增 `days` 分区，向后兼容。

### 6.5 验收标准

1. 杀进程（真机"强行停止"）→ 重开 → 昨天/前天的日志仍可见。
2. 篡改系统时间模拟第 4 天 → 第 1 天数据被整日清除，且伴随一条 `log.retention` 的 info 记录。
3. 连续灌入 2000 条 debug → 当日仍在 800 条上限内，warn/error 一条不丢。
4. 导出文件 ≤ 2MB，文件名含起止日期；导出后目录内旧文件按策略清理。
5. 日志页首屏渲染 < 300ms（3 天、约 2400 条时）。
