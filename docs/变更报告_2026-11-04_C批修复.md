## 三、逐文件说明

### 1. Android 原生（6 处）

**`CaptureKeepAliveService.java`** — 常驻通知 `setSmallIcon` 从系统默认 `android.R.drawable.ic_menu_manage`
改为品牌图标 `app.financemanager.local.R.drawable.ic_capture_notification`。
该图标资源**已存在**（`app/src/main/res/drawable/ic_capture_notification.xml`），引用无悬空。

**`PaymentShareActivity.java`** — 两处：
- Toast 文案"财务经理"→"私人记账"（品牌名对齐）。
- `writeCaptured` 成功后补一行 `PaymentCapturePlugin.launchRecordForCapture(this.getApplicationContext(), entity)`。
  原因：此前分享链路只推事件不拉起 APP，Toast 却承诺"即将打开私人记账"，用户停留在微信里等空。
  方法与无障碍/通知链路对齐（该方法已在 `PaymentCapturePlugin.java:899` 定义并被另两处使用，签名匹配）。

**`MainActivity.java`** — 任务中心遮罩（`onWindowFocusChanged(false)` 时提前盖白防截图）品牌化：
文案"财务经理"→"私人记账"，背景白→`#F4F6F3`，文字色→`#98A19E`。

**`strings.xml`** — `share_activity_label` 由"私人记账-记账"→"私人记账"（去重复后缀）。

**`styles.xml`** — `AppTheme.NoActionBar` 与 `Theme.OverlayTransparent` 由 `Theme.AppCompat.DayNight.*`
改为 `Theme.AppCompat.Light.NoActionBar`。原因：前端锁定浅色（index.html `color-scheme: light`），
DayNight 会让系统深色模式下的原生弹窗（日期选择/确认框）翻成深色挂在浅色页面上。

**`colors.xml`（新增）** — 定义 `colorPrimary`/`colorPrimaryDark`/`colorAccent`/`background`。
原因：此前未定义，`styles.xml` 引用的 `@color/colorPrimary` 等落在 Capacitor 库默认靛蓝上，
原生弹窗强调色与 App 品牌（绿/金）脱节。**新增无重复资源冲突**（此前无本地 colors.xml）。

### 2. 前端（6 处）

**`App.vue`** — 仅删除一条残留注释（"当场弹窗记账：原生侧检测到支付完成后…"）。
对应的 `capture-quick` 组件已在提交 `b04197a` 整体删除，此处纯清理，**无功能变更**。

**`RecordSheet.vue`** — 3 处：
- `canSubmit`：金额校验改用 `parseCnyInputToMinor()` 的 try/catch 判定（>0 且最多两位小数），
  替代原枚举 `'0'/'0.0'` 黑名单——`'0.00'` 等形态此前会漏过白名单、到 submit 才报错。
- `initializeFormState`：补重置全部捕获元数据（`captureSource/captureParserVersion/captureConfidence/
  captureDirection/captureHintVisible/captureFingerprint/captureId`）。
  原因：KeepAlive 复用同一实例，残留的 fingerprint/captureId 会让"放弃捕获预填后的手动记账"
  在保存时误标指纹/误删待确认事件；captureHintVisible 残留会把备注+金额输入行永久替换成方向提示。
- 手续费分支：`amountStarted` 时把金额框抬到**申请额**（净额 + fee）。
  原因：Android 捕获语义 `amountMinor` 是"实到金额"、`originalAmount = 实到 + fee`（申请额），
  若不抬，保存时"申请额 - fee"会把手续费双重扣减。

**`app-lock-service.ts`** — 2 处：
- `verifyPin`：PBKDF2 迭代次数改读存储串自带值（`iterStr`），而非固定 `PBKDF2_ITERATIONS`。
  原因：未来调高迭代次数时，存量哈希仍可验证（不再因常量变化而锁死旧 PIN）。
- 升级存储格式时，用 `Promise.all` 一并清除不再需要的旧盐 `APP_LOCK_PIN_SALT_KEY`。

**`backup-service.ts`** — `verifyBackupJson` 的 `totalRecords` 计算排除 `schema_migrations`。
原因：`schema_migrations` 不参与恢复（见 `backup-repository.ts:292` 的 `replaceAll` 过滤），
否则新装机的"空备份"（仅 15 条迁移记录）能通过校验，恢复会清空当前库且不写入数据。
**已验证与 `replaceAll` 实现一致**（restore 侧确实排除 `schema_migrations`，JSDoc 同述）。

**`capture-inbox-service.ts`** — `confirmEvent` 中 `direction === 'refund'` 也走 `createIncome`。
原因：refund = 退款到账（钱进来了），按收入入账；走 `createExpense` 会把退款记成支出（方向反转）。
退款关联原单的场景需用户在完整记账页用退款流程处理，一键确认没有该上下文。

**`CaptureInboxView.vue`** — 4 处：
- `isIncomeEvent` 纳入 `refund`（确认弹窗分类池/方向正确）。
- `goRecordPage`：`occurredAt` 经新增的 `normalizeOccurredAt()` 归一化——队列可能残留旧版**毫秒串**，
  统一转 ISO（非法值返回空串，由记账页回退当前时间）。
- `doDismiss`/`doDismissAll`：包 try/catch，失败时给用户提示"忽略失败，请重试"（此前静默失败）。
- 健康条无障碍项状态用 `health.accessibility.connected ?? health.accessibility.enabled`。
  原因：服务"设置开着但被 MIUI 杀掉"时 `enabled=true` 但 `connected=false`，应显示未连接。

## 四、我接手后修复的一处（半成品 → 完成）

`CaptureInboxView.vue` 第 71 行附近，本地声明的 `health` ref 类型：

```ts
// 改前：accessibility 只有 enabled —— 第 286 行访问 .connected 会类型报错
accessibility: { enabled: boolean }
// 改后：补上 connected 字段（运行时 ServiceHealth 本就有，仅类型层漏了）
accessibility: { enabled: boolean; connected?: boolean }
```

**结论：这不是逻辑 bug，是类型没跟上。** 运行时 `getServiceHealth()` 返回的 `ServiceHealth`
（`payment-capture-reader.ts:47`）本来就带 `connected`，只是组件本地类型定义漏了。
已补齐，类型检查通过。
